# TD-163 — debug-проверка pacing повторно загружает конфигурацию

Статус: DONE_SCOPED_PUBLISHED_1.0.117.
Исходники, сборка, установленные байты, короткие native-контроли, CI и публикация проверены. Владелец: docs/development/release-1.0.117-debug-config-publication.md.

Карта фактического источника:
src/bin/lay_daemon/exact_ime_tail_replay.rs::execute
 → kde/firefox_replay_pacing.rs::use_fast_replay
 → LayConfig::load().debug_action_log
 → src/config/load.rs::load
 → runtime_flags::publish_runtime_config.

Подтверждённый кодом факт: даже выключенная отладка вызывает полную загрузку
конфигурации при выборе pacing. load() также публикует общие runtime-флаги,
включая включение независимого контура раскладки. Диагностическая проверка
не должна становиться вторым инициатором публикации конфигурации.
Фактическое влияние на задержку и воспроизведение рассогласования пока не
измерены; не объявлять закрытыми быстрые оконные FAIL на основании этой карты.

Соседнее готовое решение уже существует: публичная
lay::config::runtime_debug_action_log() читает опубликованные атомарные флаги;
первичная инициализация сохраняет обычный загрузчик. Нового кеша не нужно.

Минимальный план:
1. В изолированном тесте опубликовать конфигурацию и создать отличающийся файл
   на диске, не проходивший штатный reload. Вызвать настоящий use_fast_replay
   с неразрешённым fast scope, чтобы не требовался KWin. Проверить, что простая
   debug-проверка не меняет ранее опубликованный fragment/runtime-флаг.
   Получить RED на текущем источнике. Не подменять всю функцию своей моделью.
2. Проверить штатный путь обновления конфигурации и владельца публикации флагов.
   Сохранить его; изолированная задача не разрешает менять общий config loader.
3. Кандидат минимальной правки — одна строка в KDE pacing leaf: использовать
   существующий runtime_debug_action_log(). Общие flags/loader/IME/output
   не изменять. Доказать GREEN и корректное чтение ON/OFF после штатной публикации.
4. Измерить реальное число чтений конфигурации/время на том же входе без
   изменения дедлайнов. Указать отдельно startup и прогретый путь. Изолировать
   тест глобальных флагов через существующий тестовый исполнитель.
5. Выпускные source/build/CI/Security и updater ворота обязательны. Публичные
   утверждения о скорости ограничивать фактически измеренным; соответствующие
   оконные результаты не заменять тестом атомарного флага.

Риски: сохранение единственного владельца конфигурации, корректная startup-
инициализация, видимость штатных изменений меню, отсутствие ложных публикаций
контура ENG↔RU. Отладочная запись по-прежнему содержит только флаги/длины.
Никаких новых фокусов,кешей,маршрутов доставки,ретраев или тайм-аутов.
Rollback ограничен строкой leaf и её регрессией; не откатывать конфигурацию
пользователя и не перезапускать GNOME ради проверки этой задачи.
