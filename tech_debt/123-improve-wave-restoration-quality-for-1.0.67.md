## Как доказать «стала лучше»

- Сравнение одной и той же fixed proof выборки до/после: aggregate и каждый
  error class отдельно. Не скрывать регрессию класса улучшенным средним.
- Для L1 действует контракт проекта: strict unique top-1 >95% для каждого
  damage class; отдельно clean preservation, lattice coverage, false certainty,
  package/RSS budgets и latency. Один хороший показатель не заменяет остальные.
- Отдельные denominators: найденные/удержанные/выбранные кандидаты, допустимые
  применения, фактические правильные замены, ложные замены и сохранённый clean
  текст. Routing/avoided work не являются proof качества.
- Все три профиля «Осторожность», wrong-layout/mixed-input и обычные опечатки
  измеряются раздельно. Не обещать одинаковую Apply-долю у разных safety profiles.
- Измерять cold/warm latency и хвост задержек, CPU/RSS; не покупать качество
  зависаниями интерфейса, неограниченным поиском или увеличением Space deadline.
