в него синтетические клавиши. Обновление пользователя — через меню Lay.

изоляции интеграций. Она не отменяет C01–C10, не разрешает обход verifier,
нескольких владельцев или копии исполнительных маршрутов. Для каждого релиза
сначала карта влияния и точный preflight, затем реализация и доказательства.
Особенности среды/клиента находятся в адаптерах; общее решение, ownership,
верификация и единственный исполнитель сохраняются за текущими владельцами.

## Обязательный цикл каждого релиза

1. Зафиксировать commit/dirty delta, работающие байты, владельца, первый отказ,
   область, последствия и откат. Записать результаты в owning document.
2. Использовать существующие редьюсеры, worker, данные и адаптеры; RED/GREEN для
   реального инварианта и масштабированные проверки всех затронутых потребителей.
3. Согласовать все номера версии до freeze без запуска legacy bump, который
   устанавливает модели и перезапускает локальный GNOME.
4. Выполнить канонические source/release gates, все устанавливаемые бинарники,
   отсутствие новых compiler warnings, MSRV, security/public checks и бюджет.
5. Установить конкретные compiler-artifact байты только на тестовый удалённый
   runtime, сверить `/proc` и версии. Провести принятие затронутых полей и
   контроль незатронутых адаптеров. FAIL не становится PASS из-за source tests.
6. Commit/push без force; проверить CI, опубликовать stable tag/release с точными
   улучшениями, ограничениями и доказательствами. Не объявлять старые матрицы
   текущими для новых байтов.
7. Проверить опубликованные tag/assets/source и действующий updater --check:
   stable API, версия source/installed/tray, наличие нужного обновления. Локально
   обновление не устанавливать. Сохранить состояние, перейти к следующему пункту.

Никаких вопросов пользователю в рамках этого поручения. При препятствии менять
подход, сохранять доказательства и продолжать независимую работу. Не ослаблять
правила ради числа релизов. По завершении всей серии — звук установленным hook.
