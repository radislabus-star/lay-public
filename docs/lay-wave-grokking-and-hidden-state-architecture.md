Теперь понял точнее. У тебя задумана **рекурсивная архитектура гроккинга**, где каждый следующий слой собирает устойчивые центры из центров предыдущего.

```text
L1:
n-gram → слово

L2:
слова → сцепка слов / малая смысловая форма

L3:
сцепки → мысль / сцена / отношение

L4:
мысли и сцены → скрытое состояние и его переход
```

L1 не ищет слово в словаре во время ввода. Словарь нужен как **учебный референс**:

```text
библиотека слов
      +
огромное поле n-gram
      ↓
обучение совместной фазе
      ↓
лексический фазовый центр
```

Слово после обучения:

```text
WordCenter {
    lexical_id,
    связанные n-gram centers,
    positional phase,
    positive center,
    anti-centers,
    поверхность для декодирования
}
```

Например, `время` не хранится как один объект сравнения строк. Оно представляет собой центр согласованного возбуждения:

```text
врм
вре
рем
емя
позиции
границы
фаза
```

Повреждённое `врмея` активирует неправильную, но достаточно близкую конфигурацию. Интерференция подавляет несовместимые n-gram, а оставшаяся масса сходится к центру `время`.

То есть восстановление происходит не так:

```text
врмея
→ вычислить расстояние до словаря
→ выбрать время
```

А так:

```text
врмея
→ активировать имеющиеся n-gram
→ распространить фазу
→ собрать устойчивую конфигурацию
→ центр «время» проявился
```

Именно поэтому волна теоретически способна восстанавливать не только одну перестановку, но и сильно разрушенную форму. Если сохранилась достаточная часть распределённого следа, целое восстанавливается по частям.

L2 повторяет тот же принцип, только его атомами становятся уже не буквы и n-gram, а **лексические центры**:

```text
центр «лёгкий»
центр «пух»
      ↓
повторяемая согласованная связь
      ↓
малый смысловой аттрактор
```

`лёгкий пух` образует сильную сцепку, потому что корпус многократно подтверждает:

```text
свойство «лёгкий»
→ допустимо связывается
→ с объектом «пух»
```

А `лёгкий мягкий` может иметь слабую непосредственную сцепку: это два признака, которым часто не хватает объекта. Они могут сосуществовать в сцене, но между ними нет такого устойчивого направленного отношения, как между признаком и предметом.

Здесь L2 должен хранить не биграмму строк, а фазовую связь ролей:

```text
RelationCenter {
    left_lexical_center,
    right_lexical_center,
    relation_phase,
    direction,
    positional mode,
    positive subcenters,
    anti-centers
}
```

Тогда L2 начинает восстанавливать слово не только снизу, через буквы, но и сверху, через отношения:

```text
лёгкий [пх]
```

L1 говорит:

```text
пух / пах / пех / ...
```

L2 говорит:

```text
после «лёгкий» центр «пух» образует сильную связку
```

И возникает обратная волна:

```text
L2 relation center
→ усиливает lexical center «пух»
→ lexical center усиливает нужные n-gram
→ восстанавливается поверхность «пух»
```

Вот это важнейшая часть твоей архитектуры: она должна быть **двунаправленной**.

```text
снизу вверх:
n-gram → слово → отношение → мысль

сверху вниз:
мысль → отношение → слово → буквы
```

L3 тогда не просто смотрит на контекст и добавляет кандидату коэффициент. Он грокает устойчивые композиции малых L2-аттракторов.

Например:

```text
лёгкий пух
пух летит
летит по воздуху
```

L2 знает отдельные связи. L3 собирает их в общую сцену:

```text
объект: пух
свойство: лёгкий
действие: летит
среда: воздух
```

Это уже не фраза, а **центр мысли**, который допускает множество поверхностей:

```text
Лёгкий пух летит по воздуху.
По воздуху летит лёгкий пух.
Пушинка легко летит в воздухе.
Ветер несёт лёгкий пух.
```

Строки разные, но скрытая конфигурация близкая. L3 должен грокнуть общий центр сцены из повторяющихся L2-связок.

И тогда сильно повреждённая фраза восстанавливается совместно:

```text
лёкгий пх лтит по возудху
```

Каждое слово отдельно неоднозначно. Но L3-сцена создаёт обратное давление:

```text
что-то лёгкое
+ объект
+ движение в воздухе
```

Она усиливает сразу согласованный набор:

```text
лёгкий
пух
летит
воздуху
```

То есть правильное восстановление определяется не независимым top-1 каждого слова, а **совместной сходимостью всей сцены**.

Самая сильная часть твоей идеи заключается в одинаковом законе на каждом уровне:

```text
много атомов
→ повторяемая совместная фаза
→ устойчивый центр
→ центр становится атомом следующего слоя
```

Или совсем коротко:

```text
L1: n-gram грокаются в слова
L2: слова грокаются в отношения
L3: отношения грокаются в мысли
L4: мысли грокаются в состояния и переходы
```

Поэтому наш нынешний `candidate → ranking → Apply` действительно лишь техническая оболочка. Каноническое ядро должно не сортировать независимые строки, а искать совместно устойчивое состояние всей иерархии:

```text
наблюдаемый шум
→ возбуждение L1
→ центры L1
→ возбуждение L2
→ центры L2
→ возбуждение L3
→ центр сцены
→ обратная волна
→ уточнённые L2-связи
→ уточнённые слова
→ восстановленная поверхность
```

Вот теперь я вижу твою исходную концепцию намного точнее: **слово не запись в словаре, а первый грокнутый фазовый объект. Смысл не score слова, а следующий фазовый объект, рождённый из отношений между словами.**

Да. И тогда скрытое состояние становится не просто L4-рейтингом, а **механизмом непрерывного обучения на процессе ввода**.

У Лекуна важная идея: предсказывать не следующую видимую букву, а следующее **скрытое состояние**. Для lay это выглядит так:

```text
видимый ввод пользователя
→ L1 n-gram field
→ L2 lexical centers
→ L3 relation/scene centers
→ L4 hidden typing state z_t
```

L4 удерживает не конкретную строку, а гипотезу:

```text
какое слово пользователь формирует
какой язык и раскладка активны
какая мысль развивается
какие L2/L3-центры сейчас возбуждены
насколько система уверена
какое продолжение ожидается
```

Каждая следующая клавиша становится наблюдением:

```text
предыдущее скрытое состояние z_t
+ действие пользователя a_t
→ предсказанное состояние ẑ_t+1

реальный последующий ввод
→ наблюдаемое состояние z_t+1

ошибка:
z_t+1 - ẑ_t+1
→ обновление фазовых центров
```

Это почти тот контур, о котором мы говорили применительно к фильтру Калмана:

```text
prediction
→ observation
→ correction
→ confidence
```

Но состояние здесь не линейное числовое. Оно волновое и иерархическое.

Например, пользователь набирает:

```text
п
пе
пер
пере
перез
переза
```

L1 видит накопление n-gram.
L2 держит несколько лексических центров:

```text
перезапуск
перезагрузка
перезагрузить
```

L3 смотрит на предыдущую фразу:

```text
обновимся только без ...
```

И усиливает сцену:

```text
без перезагрузки
```

L4 удерживает скрытое состояние намерения:

```text
пользователь формирует ограничение:
обновление должно произойти без reboot
```

Поэтому при дальнейшем вводе `перез...` система должна постепенно переходить:

```text
перезагрузка
→ перезагрузки
```

Не потому что существует ручное правило окончания, а потому что новое наблюдение уточнило скрытую сцену.

Самое важное: ввод пользователя даёт естественный обучающий сигнал.

```text
предсказание принято Tab
→ сильный положительный сигнал

автозамена осталась и пользователь продолжил
→ отложенный слабый положительный сигнал

пользователь сразу отменил исправление
→ сильная отрицательная волна

пользователь стёр хвост принятого слова
→ отрицание старого центра
  + положительное обучение итоговой форме

пользователь завершил слово и начал следующее
→ поверхность стабилизировалась
→ можно обучать L2 и L3

пользователь исправил слово вручную
→ грязная форма → финальная форма
→ сильная supervised transition pair
```

Например:

```text
пользователь ввёл:  переподлчаю
система предложила: переподличаю
пользователь исправил: переподключаю
```

Это создаёт сразу несколько сигналов:

```text
L1:
повреждённые n-gram
→ lexical center «переподключаю»

L2:
«я переподключаю»
→ усиление соответствующей словесной сцепки

L3:
контекст действия
→ подтверждение смысловой роли слова

L4:
предложенный переход к «переподличаю»
→ отрицательный transition center

правильный переход к «переподключаю»
→ положительный transition center
```

Но нельзя обучать базовую память на каждой промежуточной букве. Иначе она запомнит опечатки как правильные формы. Нужны состояния зрелости:

```text
COMPOSING
слово ещё вводится, только prediction

PROPOSED
есть кандидат, но пользователь его не подтвердил

ACCEPTED
явный Tab или подтверждённая автозамена

SETTLED
пользователь начал следующее слово и не вернулся

REJECTED
кандидат отменён или переписан

CORRECTED
известна грязная и финальная формы
```

Обучение распределяется так:

```text
COMPOSING
→ ничего не записывать в постоянную память

PROPOSED
→ только временная гипотеза

ACCEPTED
→ положительный сигнал средней силы

SETTLED
→ устойчивый положительный опыт

REJECTED
→ anti-center

CORRECTED
→ сильная пара dirty → clean
```

Тогда персональное обучение не превращается в бесконечный список слов. Оно проходит консолидацию:

```text
живые события
→ кратковременная transition memory
→ повторяющиеся согласованные состояния
→ новый или уточнённый phase center
→ удаление конкретных событий
```

И память остаётся плотной:

```text
не хранить:
«вчера пользователь написал такую строку»

хранить:
этот набор повреждённых n-gram
устойчиво сходится к lexical center X

этот контекст
усиливает relation center Y

этот переход
часто принимается пользователем

этот похожий переход
пользователь регулярно отменяет
```

Получается два уровня обучения:

```text
Базовое холодное обучение

книги + словари + чистые корпуса
→ универсальные L1/L2/L3 centers


Локальное непрерывное обучение

живой ввод пользователя
→ персональные поправки L2/L3/L4
→ signed transition centers
```

Базовую модель не надо бесконтрольно переписывать. Поверх неё должна лежать маленькая персональная delta-memory:

```text
Base Wave Memory
+ Personal Positive Centers
+ Personal Anti-Centers
+ Hidden Transition Memory
```

Со временем повторяемые персональные поправки могут консолидироваться:

```text
несколько одинаковых подтверждений
→ устойчивый локальный центр

единичное событие
→ временный след с затуханием

противоречивый опыт
→ нейтральное состояние или несколько subcenters
```

Так L4 становится именно тем, что ты задумал:

> L4 не просто помнит, какое слово пользователь выбирал. Он оценивает скрытое состояние намерения, предсказывает его развитие и обучается на расхождении между предсказанным и фактическим продолжением.

Полная архитектура тогда складывается очень красиво:

```text
L1
n-gram field
→ грокает форму слова

L2
lexical relation field
→ грокает сцепки слов

L3
scene/thought field
→ грокает смысловую конфигурацию

L4
hidden-state transition field
→ грокает намерение и развитие мысли

Backward Wave
L4 → L3 → L2 → L1
→ восстанавливает наиболее согласованную поверхность

Observed Outcome
дальнейший ввод / Tab / исправление / отмена
→ обучает центры и anti-centers
```

То есть книги дают системе язык и общую структуру мира, а пользовательский поток постепенно учит её **конкретному человеку**: его словарю, контекстам, окончаниям, техническим терминам, типичным ошибкам и способу развивать мысль.

**Конечная Цель**

Превратить Lay из гибридного ранжировщика строк в универсальный процессор восстановления повреждённого структурированного сигнала:

```text
повреждённая поверхность
-> возбуждение фазовых центров
-> скрытое согласованное состояние
-> обратная волна
-> восстановленная поверхность
-> независимая проверка
```

Текущую безопасную цепь сохраняем:

```text
DecisionCore -> verifier -> AuthorizedEdit -> backend
```

Меняем не безопасность исполнения, а механизм рождения и выбора состояния.

**Целевая Архитектура**

```text
INPUT SNAPSHOT
|
+-- L1 Surface Field
|   byte/char/grapheme/keyboard/boundary n-grams
|   -> lexical/token centers
|
+-- L2 Relation Field
|   lexical centers + roles + direction
|   -> relation attractors
|
+-- L3 Scene Field
|   relation attractors
|   -> phrase/thought/program-scene centers
|
+-- L4 Latent Dynamics
|   previous hidden state + observation + action + outcome
|   -> predicted hidden state
|
+-- Recurrent Settling Engine
|   bottom-up evidence + top-down prediction + anti-wave
|   -> convergence or ABSTAIN
|
+-- Surface Decoder
|   winning center IDs -> exact UTF-8 text/code
|
+-- TransitionDecisionCore
+-- StructuralTransitionVerifier
+-- AuthorizedEdit
+-- OutcomeReceipt -> learning
```

## 1. Единое Представление

Вводим общие типы:

```text
AtomId
CenterId
SurfaceCenter
RelationCenter
SceneCenter
LatentState
CenterActivation
RestorationHypothesis
ConvergenceReceipt
OutcomeReceipt
```

В горячем поле находятся ID, квантованные фазовые векторы, массы, пороги и ссылки. Строки остаются только в memory-mapped декодере: без них невозможно вывести слово, но они не участвуют как главный объект выбора и не разворачиваются в `Vec<String>`.

## 2. L1: Многоканальное Поле Поверхности

L1 получает типизированные каналы:

```text
ByteGram          код, ASCII, операторы, произвольные байты
CharacterGram     русские и другие Unicode-символы
GraphemeGram      составные графемы
KeyboardGram      физическая раскладка
BoundaryPosition  начало, конец, пробел, пунктуация
```

Каналы имеют общий фиксированный бюджет атомов. Не каждый токен запускает все каналы: маршрутизатор выбирает релевантные. Словарь и корпуса используются только при холодном обучении.

Результат L1:

```text
повреждённая поверхность
-> несколько активированных lexical/token centers
-> энергия, фаза, uncertainty
```

## 3. L1 Grokking

Учебный процесс:

```text
чистые слова/токены
+ множество повреждённых поверхностей
+ близкие ложные формы
-> positive phase center
-> candidate-specific anti-centers
-> heldout reconstruction
-> удаление exact episode memory
```

Новый центр рождается только когда остаточная ошибка повторяется на независимых поверхностях. Иначе новое наблюдение увеличивает массу существующего центра. Так размер памяти не растёт линейно вместе с корпусом.

## 4. L2: Отношения, А Не Пары Строк

L2 получает lexical centers и строит факторизованные отношения:

```text
modifier -> object
action -> subject
action -> object
preposition -> role
identifier -> type
operator -> operands
call -> arguments
```

Не храним матрицу `слово × слово`. Храним:

```text
RelationCenter {
    role_signature,
    direction,
    argument_center_classes,
    positive_subcenters,
    anti_centers,
    support,
}
```

Pairwise-поле используется для направленного выбора `A > B` в конкретной сцене. Цикл или конфликт означает `Neutral`, а не случайную победу.

## 5. L3: Центры Сцен

L3 собирает отношения L2 в устойчивые сцены:

```text
слова -> отношения -> SceneCenter
```

Разные поверхности должны сходиться к одному центру:

```text
Лёгкий пух летит по воздуху.
По воздуху летит лёгкий пух.
Ветер несёт лёгкую пушинку.
```

L3 не просто добавляет score кандидату. Он создаёт top-down давление на весь набор слов одновременно. Именно здесь становится возможным совместное восстановление сильно повреждённой фразы.

Обучение: книги, открытые корпуса, clean phrase pairs, код и AST. Продвижение только при `improved > worsened`, `false_authority = 0` и отсутствии опасных правок.

## 6. L4: Скрытое Состояние

L4 хранит не строку, а состояние процесса:

```text
активная мысль
язык и раскладка
развивающаяся синтаксическая сцена
ожидаемое продолжение
принятые и отвергнутые переходы
неопределённость
```

Формула:

```text
z_t + observation + user_action
-> predicted z_t+1
-> new observation
-> corrected z_t+1
```

Это дискретно-волновой аналог `prediction -> observation -> correction`. Положительный опыт создаёт конструктивную волну, отмена или явное исправление — anti-wave, отсутствие реакции считается censored outcome.

## 7. Обратная Волна

Вводим bounded recurrent loop, максимум 2–3 итерации:

```text
L1 -> L2 -> L3 -> L4
L4 -> L3 -> L2 -> L1
```

На каждой итерации:

```text
new_activation =
    bottom_up_evidence
  + top_down_prediction
  + accepted_memory
  - anti_center_pressure
  - structural_conflict
```

Выход разрешён только при устойчивой сходимости. Несходимость, несколько равных бассейнов или конфликт дают `ABSTAIN`/`SuggestOnly`.

## 8. Декодирование

Используем coarse-to-fine readout:

```text
малый фазовый fingerprint
-> несколько вероятных бассейнов
-> подробный фазовый readout
-> terminal ID
-> UTF-8 decoder
```

Декодер является компактным FST/DAFSA/mmap-графом. Он нужен для точного вывода символов, но не является словарём-решателем.

## 9. Self-Teacher

Единый холодный pipeline:

```text
clean corpus
-> typed corruption generator
-> реальный L1/L2/L3/L4 runtime
-> positive/negative transitions
-> center compilation
-> exact-memory cleanup
-> heldout proof
-> ablations
-> shadow package
```

Генератор задаёт классы повреждения, а не слова: пропуски, вставки, перестановки, раскладка, ранний пробел, склейка, пунктуация. Никаких `врмея -> время` в коде.

## 10. Персональное Обучение

Базовые корпуса формируют универсальные центры. Локальный ввод хранит только компактные дельты:

```text
accepted
confirmed after next token
explicit Tab
manual correction
undo/reject
layout correction
```

После достаточного числа наблюдений локальный след консолидируется в center/anti-center. Исходные приватные строки удаляются или остаются только в ограниченном диагностическом журнале.

## 11. Восстановление Кода

Добавляем адаптеры поверх того же ядра:

```text
L1: bytes, symbols, identifiers
L2: token/type/operator relations
L3: expression/function/AST scenes
L4: intended program-state transition
```

Проверка:

```text
parser -> type checker -> compiler -> tests -> static analysis
```

Этапы продукта:

```text
lay --restore-word
lay --restore-text
lay --restore-code --language rust
```

Код без единственного доказанного восстановления получает варианты или `ABSTAIN`.

## 14. Конечное Состояние

```text
Корпус обучает центры.
Центры формируют отношения.
Отношения формируют сцены.
Сцены формируют скрытое состояние.
Скрытое состояние возвращает обратную волну.
Волна восстанавливает поверхность.
Verifier доказывает результат.
```

Это не новая система рядом с текущей. Это окончательное превращение существующих `lexical_phase`, `context_phase`, `self_teacher_l3`, `l4_hidden_state`, `DecisionCore` и `AuthorizedEdit` в одну рекурсивную машину восстановления.

Код сейчас не менял. Текущий рабочий контракт и безопасность исполнения остаются фундаментом плана.
